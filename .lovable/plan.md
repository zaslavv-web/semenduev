
## Как сейчас устроена работа `/admin`

### 1. Маршрут и загрузка страницы
- Файл `src/routes/admin.tsx` регистрирует роут `/admin` (TanStack Router, file-based).
- При заходе монтируется компонент `AdminPage`. На SSR/первой отрисовке показывается экран «Загрузка…».

### 2. Проверка сессии Supabase
- `supabase.auth.getSession()` — читает токены из `localStorage` браузера.
- Параллельно подписка `onAuthStateChange` обновляет `userId` при логине/логауте/восстановлении пароля.
- После ответа `getSession` снимается флаг `loading`.

### 3. Проверка роли админа
- Когда `userId` появился, делается запрос:
  `select role from user_roles where user_id = <uid> and role = 'admin'`.
- Запрос разрешён RLS-политикой «Users can view their own roles».
- Если строка есть → `isAdmin = true`, иначе → экран «Доступ запрещён».
- Пока запрос идёт — держится `roleLoading`, страница показывает «Загрузка…» (не мигает «Доступ запрещён»).

### 4. Если пользователь не залогинен → `AuthForm`
- Три режима: вход, регистрация, «забыли пароль».
- **Регистрация:** первый пользователь автоматически получает роль `admin` через триггерную функцию `handle_new_user_role()`. Все последующие — роль `user`.
- **Восстановление пароля:** `resetPasswordForEmail` с `redirectTo = origin + /reset-password`. Письмо приходит → пользователь идёт на `/reset-password`, в `__root.tsx` ловится событие `PASSWORD_RECOVERY` и при необходимости делается редирект. Истёкшая ссылка → тост об ошибке.

### 5. Если админ → `Editor`
- Грузит из таблицы `site_content` все строки `{section, data}`.
- Мерджит каждую секцию с `defaultContent` (дефолты из кода + переопределения из БД).
- Левая колонка — список секций (Hero, About, Cases и т.д.).
- Средняя колонка — `ValueEditor` рекурсивно рендерит поля (строки, картинки, объекты, массивы).
- Любое изменение → `scheduleSave` (debounce 700 мс) → `upsert` в `site_content` (RLS «Admins can update/insert»).
- Картинки заливаются в Storage-бакет `site-images` (публичный).
- Правая колонка — `<iframe src="/?preview=1#section">` с живым превью.

### 6. Как изменения попадают на сам сайт
- Главный сайт (`/`, `/privacy` и т.д.) обёрнут в `ContentProvider` (`src/lib/content/ContentProvider.tsx`).
- При монтировании провайдер:
  1. Делает `select * from site_content` (RLS «Anyone can read site content» — доступно даже `anon`).
  2. Мерджит с `defaultContent`.
  3. Подписывается на Realtime-канал `postgres_changes` для таблицы `site_content` и при любом INSERT/UPDATE/DELETE перезагружает контент.
- Компоненты сайта читают данные через `useSection("hero")`, `useSection("header")` и т.д.

## Почему связка «админка ↔ сайт» может не работать сейчас

### A. Проблемы с авторизацией в админке
1. **Сессия не сохранилась** — кука/localStorage очищены, сторонние cookie заблокированы (Safari/инкогнито) → бесконечный «Загрузка…» или редирект на форму входа.
2. **Нет роли admin** — пользователь зарегистрировался не первым; в `user_roles` для него только `user`. Запрос вернёт `null` → «Доступ запрещён». Лечится вставкой строки `('<uid>', 'admin')` в `user_roles`.
3. **RLS блокирует запрос роли** — если политика «Users can view their own roles» была изменена/удалена, `maybeSingle()` вернёт ошибку и `isAdmin = false`.
4. **Восстановление пароля** — `redirectTo` ведёт на `${origin}/reset-password`. Если домен письма (`semenduev.pro`) не совпадает с разрешёнными Redirect URLs в настройках Supabase Auth, ссылка отвалится с `otp_expired` / `access_denied`.

### B. Проблемы передачи контента из админки на сайт
1. **Realtime отключён для таблицы** — если `site_content` не добавлена в `supabase_realtime` publication, изменения долетят до сайта только после ручной перезагрузки (F5). Проверка:
   `select * from pg_publication_tables where pubname = 'supabase_realtime';`
2. **Кэш CDN / опубликованной версии** — фронт собран и опубликован, но он читает БД на лету. Если сайт открывается из старой версии без `ContentProvider` (например, кэш Service Worker, старый деплой), изменения не подтянутся.
3. **Ошибка чтения `site_content`** — RLS-политика «Anyone can read site content» удалена/изменена. Тогда `anon` не получит данные → сайт молча покажет `defaultContent`.
4. **Структура `data` в БД не совпадает с `defaultContent`** — после правок схемы в коде старый jsonb мерджится, но «лишние/недостающие» поля приводят к отсутствию текстов или поломке рендера. Лечится «Сбросить секцию» в админке.
5. **Превью в iframe не обновляется** — iframe грузит `/?preview=1`. Если сам iframe закэширован браузером, кнопка «Обновить» (`RefreshCw`) форсит перезагрузку. Это не баг связки, а UI.
6. **Разные окружения** — админка открыта на preview-домене (`*.lovable.app`), а смотрите сайт на проде `semenduev.pro`. Это **одна и та же БД**, так что данные общие, но если препрод и прод указывают на разные Supabase-проекты (что не наш случай — у нас один), данные не совпадут.
7. **Загрузка картинок в Storage** — бакет `site-images` публичный, но если у админа нет INSERT-политики на `storage.objects` для этого бакета, картинка не зальётся, а URL не подставится.

### Что проверить в первую очередь
1. Открыть `/admin` в инкогнито, залогиниться → дойти до экрана редактора.
2. В консоли Network посмотреть запрос `site_content` со страницы `/` — приходят ли данные.
3. В БД: `select * from supabase_realtime.schema_migrations;` и `select tablename from pg_publication_tables where pubname='supabase_realtime';` — есть ли там `site_content`.
4. В настройках Auth: список Redirect URLs включает `https://semenduev.pro/reset-password` и `https://semenduev.pro/admin`.
5. Изменить любое поле в админке → в DevTools сайта в табе WS должен прийти Realtime-пакет; если нет — публикация не настроена.
